## 一句话

用户输入一句话，Agent 先生成可执行的验收标准，再生成单文件 Web 应用，在隔离沙箱里逐条验收；失败自动修复一次，通过质量门禁才交付。

---

## 1. 为什么做

AI 生成应用的门槛已经很低，但“生成完能不能用”仍然是黑盒：

- 看起来能点，实际有运行时错误
- 刷新页面，数据没了
- 表单没有可访问名称
- 改一次功能，不知道有没有破坏旧功能
- 测试用例写不过来，也没法回归

传统做法是“生成完再人肉点一遍”。VibeCheck 的思路是把质量前置：**先定义什么叫“做好了”，再让 AI 写代码。**

---

## 2. 它怎么工作

1. **描述**：输入一句话，或打开一个预置模板
2. **出规格**：Spec Agent 产出应用规格 + 4-6 条可执行验收标准
3. **写代码**：Code Agent 流式生成单文件 HTML，遵守 `data-testid` 与 `app-state` 存储契约
4. **跑验收**：在 iframe 沙箱里真实点击、输入、检查 DOM 与存储，同时捕获运行时错误和无障碍问题
5. **门禁判定**：运行时 30 + 验收 40 + 可访问性 15 + 韧性 15；**≥80 且零运行时错误才放行**
6. **修复闭环**：失败自动修复 1 次；仍不达标可一键继续修复
7. **交付**：导出 HTML、报告 JSON、Playwright 用例；版本历史可回看

界面里能看到完整的 **Agent Trace**：拆需求 → 写代码 → 沙箱验收 → 门禁判定。

---

## 3. 核心差异化

大多数 AI 应用生成器停在“生成了”，VibeCheck 继续走到“验证过”。

| 常见做法 | VibeCheck |
| --- | --- |
| 生成完让人自己点 | 先生成可执行验收标准，再执行 |
| 只做静态检查 | 真实浏览器里点击、输入、读存储 |
| 失败就重试 | 带着结构化失败报告定向修复 |
| 改完不知道有没有回归 | 复用原验收标准做回归 |
| 测试是一次性的 | 验收用例可导出 Playwright，进 CI |

> **Atoms 让生成更快，VibeCheck 让生成更可信。**

---

## 4. 三个技术亮点

### 4.1 不可信代码的隔离

AI 生成的代码不能直接信任。项目用不透明源 iframe sandbox（不加 `allow-same-origin`）把它关进“隔离房间”，它读不到父页面的 DOM 和 Cookie。

沙箱里 `localStorage` 会直接抛 `SecurityError`，所以做了一层 **postMessage 存储桥**：生成代码通过 `window.__atoms.storage` 读写，父页面落到 IndexedDB。刷新后数据还在，隔离也没有被破坏。

### 4.2 Spec-driven 验收

验收不是写死的，而是根据需求生成的结构化检查：

`visible` / `input` / `click` / `expectText` / `expectStorage` / `noRuntimeErrors`

离屏 iframe 注入 runner 逐条执行，结果、运行时错误、可访问性问题通过 postMessage 回传，最后统一评分。同一组验收还能导出成 Playwright `.spec.ts`，从 Demo 变成可回归的 CI 资产。

### 4.3 流式生成 + 版本 + 本地持久化

- 流式生成：边生成边显示，不用等整段完成
- 版本历史：生成 / 修改 / 自动修复 / 模板都会留版本
- IndexedDB：项目、版本、生成应用数据全部本地保存，无需登录
- 服务端只做模型代理、限流和契约校验，不存用户数据

### 4.4 成本与安全

- API Key 只在服务端，浏览器接触不到
- 每 IP 每日调用限额，防止 key 被刷
- 生成物禁止外部依赖，保证可复现
- 3 个预置模板不配置模型也能完整体验质量门禁

## 6. 和 Atoms 的关系

- **同一产品品类**：自然语言 → Agent 生成应用 → 可视化预览
- **独立实现**：不调用 Atoms API、不嵌入 Atoms、不复用其代码和品牌
- **参考的是产品形态**，不是技术依赖；这不是 Atoms 的复刻，也不是它的插件
- **差异化是质量闭环**：生成前定契约、生成中校验、生成后验收、失败修复、用例可回归
- Atoms 的体验额度（如使用）只用于参考产品体验和对比笔记，不是项目依赖

一句话：

> 不是做 Atoms 的复刻，而是用 QA 视角补上“生成之后”的那一段。

---

## 7. 边界与下一步

**当前边界**

- 只生成单文件 HTML，不是完整多文件工程
- 验收 runner 跑在浏览器内，可信度低于真实 Playwright
- 自动修复只做 1 轮
- 限流是单实例内存实现
- 没有登录、分享链接、多人协作

**下一步优先级**

1. **P0**：20 条 golden prompt 的评估集；把导出的 Playwright 用例接进 CI
2. **P1**：失败首版入版本历史 + diff；分享质量报告；多文件/WebContainer
3. **P2**：视觉回归、模型 A/B、生成物一键部署、线上遥测

## 9. 30 秒 / 2 分钟介绍

**30 秒**

> 我做了一个叫 VibeCheck 的 AI 应用生成器。你一句话描述想要的应用，它会先生成验收标准，再写代码，然后在隔离沙箱里自动测试；不达标会自动修复一次，通过质量门禁才交付。它和 Atoms 属于同一类产品，但我是独立实现的，重点不是“生成得更快”，而是“生成完敢不敢用”。

**2 分钟**

> 先讲痛点：AI 生成的应用看起来能用，但经常有运行时错误、刷新丢数据、改完不知道有没有回归。
>
> 我的做法是把质量前置：先生成 4-6 条可执行验收标准，再让 AI 写代码；然后在沙箱里真实点击、输入、检查存储，算一个质量分；80 分以上且零运行时错误才放行，失败就带着报告自动修复一次。
>
> 技术上三个点：不可信代码用不透明源 sandbox 隔离；沙箱里 localStorage 不可用，我用 postMessage 存储桥落到 IndexedDB；验收用例可导出 Playwright，能进 CI。
>
> 结果是 3 个模板 100 分；真实模型 76 秒，首版失败、自动修复 1 次后 100 分、7/7 项通过。
>
> 我也清楚边界：单文件、浏览器内 runner、只修一轮。下一步是评估集、Playwright CI、多文件工程。
>
> 这和测试开发岗位要做的 AI 原生质量体系是同一件事：不是多找几个 bug，而是让每一次生成更可靠。
